# 五人分工、答辩稿与现场执行清单

## 一、先定“不做什么”

60 分钟比赛不要平均用力。建议明确放弃以下高风险事项：

- 不做真实图片识别模型训练；
- 不接必须联网才能运行的大模型；
- 不做用户注册、数据库、复杂权限；
- 不为每种作物写大量独立代码；
- 不在最后一刻改知识库字段结构。

本项目的比赛主链路是：**可运行的本地 RAG 诊断 + 可解释结果 + 针对性施肥建议 + 现场统计**。所有分工围绕这条链路。

---

## 二、五人角色与时间盒

### A：队长 / 后端主程（技术负责人）

**目标**：保证核心链路 40 分钟前跑通，50 分钟前冻结代码。

- 0–5 min：确认请求/响应字段，拆分 `诊断、风险、建议、来源` 四块；
- 5–25 min：完成 `DiagnosisAgentService`、检索重排、置信度与 API；
- 25–40 min：与前端联调，确保异常输入有友好提示；
- 40–50 min：只修阻断演示的问题，不添加新功能；
- 50–60 min：执行构建、启动、提交检查，准备兜底。

**答辩一句话**：我负责主链路和接口契约，优先保证“输入一次就一定出结果”，大模型不可用也不影响演示。

### B：知识库 / 数据工程

**目标**：让系统“有依据”，而不是让大模型猜。

- 0–8 min：列出氮、磷、钾、镁、铁、锌、硼、钙的判别要点；
- 8–30 min：整理 JSON：作物、部位、症状词、风险因素、四类施肥建议；
- 30–40 min：补充来源 ID、证据词与双版本文案；
- 40–50 min：核对施肥安全表述，避免写死绝对用量；
- 50–60 min：准备“数据来源与清洗流程”答辩页。

**答辩一句话**：我们把公开科普与推广资料清洗成结构化知识条目，识别时先检索本地证据，再生成建议。

### C：前端 / 交互

**目标**：让评委在 30 秒内看懂系统在做什么。

- 0–10 min：页面骨架、表单、结果区；
- 10–30 min：实现候选置信度、风险卡、双版本建议切换；
- 30–40 min：接入真实 API，补错误态与加载态；
- 40–50 min：浏览器全链路验收，检查移动端与横向溢出；
- 50–60 min：准备演示操作路径，避免现场临时找入口。

**答辩一句话**：页面不是静态效果图，所有候选、风险、建议和来源都来自后端真实响应。

### D：测试 / 集成 / 部署

**目标**：用证据证明“不是只能在我的电脑上跑”。

- 0–8 min：定 5 个必测样例：N、K、Fe、Zn、Ca；
- 8–20 min：写服务层测试，校验首要候选与建议字段；
- 20–32 min：写 API 测试，校验 200、400 和必填字段；
- 32–42 min：打包 JAR，从项目根目录启动并调用健康检查；
- 42–50 min：浏览器冒烟测试，检查控制台错误和结果区；
- 50–60 min：整理测试数字与截图，供 PPT 使用。

**答辩一句话**：当前有 7 个自动化测试，另做浏览器端到端冒烟测试；主流程通过后才冻结提交。

### E：PPT / 答辩主讲 / 思政设计

**目标**：5 分钟讲清楚“需求—方案—数据—结果—分工—亮点”。

- 0–10 min：写出 6 页 PPT 标题和一句话结论；
- 10–30 min：制作架构图、RAG 流程图、演示截图；
- 30–40 min：写思政文案和收束句，控制为 1～2 句；
- 40–50 min：计时彩排一次，准备 5 个追问；
- 50–60 min：提交材料检查，主讲答辩。

**答辩一句话**：我们没有把思政做成弹窗，而是让“科学施肥、减量增效、粮食安全”跟着施肥建议自然出现。

## 三、并行协作规则

1. **接口先冻结**：前后端只围绕 `/api/diagnose` 一个主接口联调。
2. **知识库字段不随意改**：B 负责字段，A 不改结构；确需修改先同步。
3. **主链路优先**：任何创新功能如果不能 40 分钟前完成，立即降级为 PPT 说明。
4. **演示数据固定**：现场优先使用“水稻缺氮”样例，结果最稳定、解释最直观。
5. **代码冻结时间**：T+50 min。之后只做启动、截图、PPT、答辩。
6. **唯一提交人**：A 或 D 指定一人负责最终压缩包，避免多版本覆盖。

## 四、PPT 建议结构（6 页）

### 第 1 页：题目与一句话价值

- 标题：禾诊——农作物缺素症识别与科学施肥建议智能体
- 副标题：先查本地知识，再给可解释建议
- 结论：让农户少一点盲目施肥，让 AI 真正落到田间。

### 第 2 页：需求解构

- 用户痛点：黄叶不等于缺氮，凭经验容易误判；
- 核心任务：症状输入 → 缺素候选 → 科学施肥；
- 非目标：不替代测土配方和农技人员。

### 第 3 页：系统架构

- 前端输入；
- Spring Boot API；
- 本地 JSON 知识库；
- 检索重排 + 风险预警 + 建议模板；
- 可选 Spring AI 润色；
- LangChain4j `@Tool` 扩展。

### 第 4 页：数据与 RAG

- 数据来源：公开农技科普、测土配方施肥、化肥减量资料；
- 清洗：去噪、切片、结构化；
- 检索：症状词 + 作物/部位 + 双字组相似度；
- 可信：来源 ID、证据链、置信度。

### 第 5 页：现场演示结果

放真实运行截图，而不是效果图：

1. 输入水稻下部老叶发黄；
2. Top 3 候选与置信度；
3. 沙质土风险预警；
4. 农户/农技双版本建议；
5. 证据来源和思政提示。

### 第 6 页：创新、测试与分工

- 创新：风险预警、可解释链、热重载、统计看板；
- 测试：7 个自动化测试 + 浏览器冒烟测试；
- 分工：5 人时间盒并行；
- 收束：科学施肥守护粮食安全，青年用 AI 服务三农。

## 五、5 分钟答辩逐字稿（可直接删改）

### 0:00–0:30 需求

“农户看到叶片发黄、叶缘焦枯时，很难判断到底缺什么。盲目补肥不仅增加成本，还可能造成土壤和面源污染。我们的目标不是让大模型随便猜，而是做一个能查本地知识、能展示证据、能给出科学施肥建议的智能体。”

### 0:30–1:30 架构

“系统采用前后端分离。前端负责症状输入和结果展示；Spring Boot 提供 API；核心智能体先检索本地 JSON 知识库，通过症状、部位、作物和中文双字组相似度做重排，再生成风险预警和施肥方案。Spring AI 和 LangChain4j 保留为可选增强，但断网时主链路仍然完整可运行。”

### 1:30–3:00 演示

“我们输入一个水稻样例：下部老叶先发黄、植株矮小、分蘖减少。系统给出缺氮为首要候选，同时保留磷、钾等次候选和置信度。右侧根据沙质土、降雨和分蘖期给出中风险提示。下方按农艺、有机肥、化学追施、安全减量四部分给出方案，并支持农户版和农技版切换。最后展示命中的本地证据和资料来源。”

### 3:00–4:00 创新与测试

“我们的创新点有三个：第一，候选结果可解释，能看到命中了哪些症状词；第二，风险预警结合土壤、环境和生育期；第三，知识库外部 JSON 可热重载，增加条目不用改代码。测试方面有 7 个自动化测试和浏览器端到端冒烟测试，保证主流程真实可用。”

### 4:00–5:00 价值收束

“科学施肥既要算产量账，也要算生态账。我们希望通过这个作品，让 AI 不只是一个聊天窗口，而是能帮助基层农户减少盲目施肥的工具。藏粮于地、藏粮于技，青年把技术写进田间地头，就是我们理解科技助农的方式。”

## 六、现场追问准备

### Q1：为什么不用大模型直接判断？

答：直接生成不可控、不可追溯，而且断网或没有密钥就无法演示。我们把缺素判断建立在本地知识库检索上，大模型只做可选润色，核心事实不交给它自由发挥。

### Q2：置信度怎么来的？

答：不是大模型编的。它由典型症状命中、部位/作物匹配、标签与风险条件命中、全文相似度共同组成，再用绝对分数映射到 0～100，含糊描述不会得到高置信度。

### Q3：知识库只有 8 条，够吗？

答：8 条覆盖氮、磷、钾、镁、铁、锌、硼、钙八类核心缺素，满足一小时赛题演示。结构支持通过外部 JSON 增量扩展，增加作物和条目不需要改 Java 代码。

### Q4：数据是否真实？

答：正式条目按公开农技科普、测土配方施肥和化肥减量资料做了结构化整理，并保留来源 ID。爬虫脚本负责采集、清洗和切片，但采集结果必须人工核对后入库，不直接自动污染知识库。

### Q5：施肥建议是否可以直接执行？

答：系统给出原则、方向和安全管理，不给出脱离土壤检测的万能用量。具体用量必须结合测土结果、目标产量、品种和产品标签，由当地农技人员确认。

### Q6：创新点是否真的实现？

答：风险预警、证据链、双版本模板、外部知识库热重载和统计看板都在实际代码中，不是 PPT 虚构。浏览器截图来自真实运行页面。

### Q7：为什么选择这个技术栈？

答：Spring Boot 适合快速构建稳定 REST 服务；Spring AI 保留大模型扩展能力；LangChain4j 的 `@Tool` 可以把本地检索能力开放给 Java 智能体；前端用原生 HTML/CSS/JS，减少比赛现场依赖。
